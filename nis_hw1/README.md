# Трекер подписок. Сервер

Приложение помогает следить за платными подписками. Здесь можно посмотреть, сколько стоит каждая подписка, когда будет следующее списание и сколько денег уходит на подписки за месяц.

---

## Быстрый старт

```bash
docker compose up --build
```

После запуска сервер доступен по адресам:

- http://localhost:8000/docs - Swagger UI, документация, где можно вызвать любую ручку
- http://localhost:8000/redoc - ReDoc
- http://localhost:8000/openapi.json - OpenAPI-схема
- http://localhost:8000/health - проверка, что сервер работает

Таблицы в базе создаются автоматически при запуске контейнера `api`.

Чтобы остановить сервер и удалить данные : `docker compose down -v`

### Настройки

Настройки задаются через переменные окружения. Для своих значений есть шаблон `.env.example`, его достаточно скопировать в `.env`

```bash
cp .env.example .env
```

Переменные:

- `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` - доступ к PostgreSQL, по умолчанию `tracker`, `tracker`, `subscriptions`
- `API_PORT` - порт API, по умолчанию `8000`
- `APP_TIMEZONE` - часовой пояс, по которому сервер понимает, какое сегодня число, по умолчанию `Europe/Moscow`
- `LOG_LEVEL` - подробность логов, по умолчанию `INFO`

## Требования

### Функциональные

**ФТ-1. Создание подписки** (`POST /subscriptions`)

Указываются название, цена за период, периодичность, дата следующего списания и категория. Цена должна быть больше 0. Категории: развлечения, музыка, учёба, работа, софт, здоровье и другое, по умолчанию «другое». Можно указать дату окончания пробного периода. Новая подписка сразу активна

**ФТ-2. Список подписок** (`GET /subscriptions`)

Список фильтруется по категории и статусу и сортируется по цене, цене в месяц, дате списания, названию или дате создания. Порядок бывает прямым и обратным

**ФТ-3. Просмотр одной подписки** (`GET /subscriptions/{id}`)

Если такой подписки нет, сервер вернёт 404

**ФТ-4. Редактирование подписки** (`PATCH /subscriptions/{id}`)

Меняются любые поля, кроме статуса, для него есть отдельная операция. Если поменять дату списания, следующие списания пойдут в день этой новой даты

**ФТ-5. Удаление подписки** (`DELETE /subscriptions/{id}`)

Подписка удаляется вместе с историей платежей

**ФТ-6. Смена статуса** (`PATCH /subscriptions/{id}/status`)

Подписка может быть активной, приостановленной или отменённой. Неактивные подписки не входят в расходы и ближайшие платежи, и их нельзя оплатить

**ФТ-7. Отметка об оплате** (`POST /subscriptions/{id}/payments`)

Платёж записывается в историю, а дата следующего списания сдвигается на один период. Если сумма и дата не указаны, берутся цена подписки и сегодняшний день. День списания сохраняется, например после 28 февраля дата снова станет 31 марта. Оплатить можно только активную подписку, иначе сервер вернёт 409. Дата оплаты не может быть в будущем

**ФТ-8. История платежей** (`GET /subscriptions/{id}/payments`)

Платежи идут от новых к старым, рядом показано их количество и общая сумма

**ФТ-9. Расходы в месяц** (`GET /stats/monthly`)

Считаются по активным подпискам с разбивкой по категориям. Недельная цена умножается на 52 и делится на 12, а годовая делится на 12. Суммы округляются до копеек

**ФТ-10. Ближайшие платежи за N дней** (`GET /payments/upcoming?days=N`)

N задаётся от 1 до 365, по умолчанию 7. В список попадают все списания в этом окне, поэтому недельная подписка за 30 дней появится 4 или 5 раз. Также показываются окончания пробных периодов и просроченные списания, которые не отметили вовремя.

### Нефункциональные

**НФТ-1.** Сервер написан на Python 3.11+ (FastAPI). Данные хранятся в PostgreSQL, схема управляется миграциями
- Python 3.12, FastAPI, PostgreSQL 16, миграции Alembic в [alembic/versions](alembic/versions)

**НФТ-2.** API соответствует REST. Данные передаются в JSON, сервер отвечает правильными HTTP-кодами
- при создании код `201` и заголовок `Location`, при удалении `204`
- `404` - подписка не найдена, `409` - операция невозможна, `422` - неверные данные

**НФТ-3.** Входные данные проверяются. При ошибке приходит понятное сообщение в едином формате
- цена больше 0 и не больше двух знаков после запятой
- периодичность, категория и статус проверяются по списку
- даты должны быть настоящими и лежать между 2000 и 2100 годом
- неизвестные поля не принимаются
- сообщения написаны по-русски, формат описан [ниже](#формат-ошибок)

**НФТ-4.** Документация API создаётся автоматически и открывается в Swagger UI
- страница `/docs`, у каждой ручки есть описание и указаны возможные ошибки

**НФТ-5.** Денежные суммы хранятся и считаются без потери точности
- в базе тип `NUMERIC(12, 2)`, в коде `Decimal`, в JSON суммы передаются строкой, например `"399.00"`

**НФТ-6.** Любой запрос обрабатывается не дольше 300 мс, если подписок до 1000
- в базе есть индексы по статусу, категории и дате, а даты списаний считаются без перебора
- время обработки каждого запроса видно в логе и в заголовке `X-Process-Time-Ms`

**НФТ-7.** Приложение запускается одной командой
- `docker compose up` запускает базу и сервер и сам создаёт таблицы

**НФТ-8.** Настройки задаются переменными окружения, пароли не хранятся в репозитории
- настройки читает `pydantic-settings`, есть шаблон `.env.example`, а сам `.env` добавлен в `.gitignore`

**НФТ-9.** Каждый запрос записывается в лог
- в логе есть метод, адрес, код ответа и время обработки, время также приходит в заголовке `X-Process-Time-Ms`

**НФТ-10.** Бизнес-логика (расчёт месячных расходов, сдвиг дат) проверяется автотестами на pytest
- тесты лежат в [tests/test_billing.py](tests/test_billing.py) и проверяют пересчёт в месяц, сдвиг дат и ближайшие платежи

## API

Суммы принимаются числом (`399`) или строкой (`"399.00"`). Сервер всегда отвечает строкой
с двумя знаками после запятой. Даты пишутся в формате `ГГГГ-ММ-ДД`

### Подписки

| Метод | Путь | Что делает | Ответ |
|---|---|---|---|
| `POST` | `/subscriptions` | создаёт подписку | `201` |
| `GET` | `/subscriptions` | показывает список | `200` |
| `GET` | `/subscriptions/{id}` | показывает одну подписку | `200` или `404` |
| `PATCH` | `/subscriptions/{id}` | меняет поля | `200` или `404` |
| `DELETE` | `/subscriptions/{id}` | удаляет подписку | `204` или `404` |
| `PATCH` | `/subscriptions/{id}/status` | меняет статус | `200` или `404` |
| `POST` | `/subscriptions/{id}/payments` | отмечает оплату | `201`, `404` или `409` |
| `GET` | `/subscriptions/{id}/payments` | показывает историю платежей | `200` или `404` |

Параметры списка:

- `category` - `entertainment`, `music`, `education`, `work`, `software`, `health`, `other`
- `status` - `active`, `paused`, `cancelled`
- `sort_by` - `next_payment_date` (по умолчанию), `price`, `monthly_price`, `name`, `created_at`
- `order` - `asc` (по умолчанию) или `desc`

### Аналитика

- `GET /stats/monthly` - расходы в месяц по категориям
- `GET /payments/upcoming?days=7` - ближайшие платежи за N дней

### Формат ошибок

Все ошибки имеют один формат. Он используется и для 404, если адрес не найден

```json
{
  "error": {
    "code": "validation_error",
    "message": "Ошибка валидации входных данных",
    "details": [
      {"location": "body", "field": "price", "message": "Сумма должна быть больше 0"},
      {"location": "body", "field": "period", "message": "Недопустимое значение, ожидается одно из: 'week', 'month', 'year'"}
    ]
  }
}
```

Коды ошибок:

- `validation_error` (422) - пришли неверные данные
- `not_found` (404) - подписка не найдена
- `conflict` (409) - операцию сейчас нельзя выполнить, например оплатить неактивную подписку
- `http_error` (404 или 405) - нет такого адреса или метода
- `internal_error` (500) - неожиданная ошибка на сервере

## Расчёт сумм и дат

**Сдвиг даты при оплате.** Для недельной подписки дата сдвигается на 7 дней, для месячной на месяц, для годовой на год.
Если в следующем месяце такого дня нет, используется последний день месяца. Исходный день сервер хранит в поле `billing_day`, поэтому подписка с 31 января переходит на 28 февраля, а потом снова на 31 марта

**Окно ближайших платежей.** Окно начинается сегодня и длится `days` дней. Например, при `days=7` и 8 октября в него попадут даты с 8 по 14 октября. Текущую дату сервер определяет по часовому поясу из `APP_TIMEZONE`

**Просроченный платёж.** Это списание, дата которого уже прошла, но оплату ещё не отметили. Оно получает `overdue: true` и входит в сумму к оплате

**Конец пробного периода** показывается отдельным событием `trial_end`. В сумму к оплате он не входит, потому что первое списание после пробного периода и так есть в списке как обычный платёж

## Тесты

```bash
docker compose run --rm api pytest
```

Тесты из [tests/test_billing.py](tests/test_billing.py) проверяют основные расчёты: цену в месяц, сдвиг дат, ближайшие платежи, просрочки и пробные периоды.
Базу данных эти тесты не используют, поэтому запускаются и без Docker. Для этого нужен Python 3.11 или новее и зависимости из `requirements.txt`
